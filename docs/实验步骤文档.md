## 步骤 008 — 共享显存补测（2026-09-26 凌晨，用户质询后补证据链）

- **协议**：用户质询"没测共享显存怎么知道不是溢出"（铁律：性能骤降先查共享显存）。用 `research/src/gpu_mem_monitor.ps1`（WDDM 溢出藏 Shared 段、per-process 归因）全程监控，spec 组与无草稿组各跑 32k/100k（衰减最重两点，热身+3 重复），判据 = 工具自带权威判据（行为签名 + shared 增长 ⇒ 溢出；行为签名 + 无 shared 增长 ⇒ 非溢出）。
- **操作**：监控器 191 样本（实际 ~5s/样本）贯穿两臂；按引擎活跃段切分，解剖推断进程（python）的 Shared 轨迹与 adapter_shr/ded。
- **结果**：
  - **spec 组**：python Shared 启动峰 850MB → 回落 **422MB 常驻**，此后 7 分钟（覆盖 32k×3 与 100k×3 全部 prefill/decode）**±2MB 无起伏**；ded 15,580/16,303MB（逼近卡顶，余量 723MB）。
  - **无草稿组**：python Shared **98-106MB 全程平**；ded 14,868MB。
  - 两组 decode 吞吐与步骤 007 完全复现（spec 32k 32.7/100k 18.0；无草稿 54.0/50.3）。
- **判定**：**溢出排除（仪器背书）**——衰减 6 倍发生时共享显存平如水，符合"行为签名 + 无 shared 增长 = 非溢出"判据；O(L) 归属 spec 管线的定罪维持。**两个附带发现记档**：①spec 路径常驻多占 ~316MB WDDM shared（装载期分配、非运行期溢出，T-perf 顺带查是什么分配的）②spec 组显存逼近卡顶，200k 级配方需盯余量。采样粒度 5s（工具 Get-Counter 上限），持续型溢出可检出、亚秒级突发理论上可漏——但 6× 慢化必是持续型，不影响判定。

## 步骤 007 — A5 长上下文锚终采 + 性能基线矩阵 + spec 管线 O(L) 定罪（2026-09-25 深夜）

- **协议**：按最终口径（无溢出配置、热身弃 1、3 重复取中位、真 token 计）采 A5 长上下文锚；补无草稿基线矩阵（用户基准锚 57-60 tok/s，参照 `run_qwen_textonly_offload_200448_stable.cmd`）；用"无草稿 vs 带草稿"的长度曲线隔离长上下文衰减的归属（目标模型内核 vs 投机解码管线）。
- **操作**：三组采集——①A5（N=2、池 3.6e9 贴合 121,776、去 prefix-cache/offload）8k/32k/100k/115k；②无草稿基线（同池）4k/8k/32k/100k；③N=3 复现组（步骤 006 遗留）。115k 档 400（错误体未捕获，待查，不影响 100k 内锚）。
- **结果**（稳态 tok/s 中位，needle 全中）：

  | 配置 | 4k | 8k | 16k | 32k | 100k | 步长走向 |
  |---|---|---|---|---|---|---|
  | 无草稿（基线） | **55.7** | **55.6** | — | **54.2** | **50.3** | 17.9→18.4→**19.8ms**（几乎平） |
  | N=2 spec（A5 锚） | — | 57.5 | — | 34.1 | **18.9** | 39→61→**129ms**（O(L) 增长） |
  | N=3 spec（复现） | 64.8（峰 72） | 57.6 | 41.8 | — | — | ~35ms（短上下文） |

  无草稿基线与用户基准 57-60 **吻合**；runner 原口径 N=3 doc_4k = 83.33（步骤 006）。spec 步长 = 无草稿 2.2×（短上下文）且**随长度线性恶化**（~0.9µs/token，100k 处 +110ms/步）。
- **判定**：**长上下文 decode 衰减 100% 归属投机解码管线的 O(L) 每步开销**，目标模型 attention 内核无罪（100k 时注意力 KV 读实测仅 ~2ms/步，接近 DRAM 满带宽）；当前生产配置 100k 处带草稿比无草稿慢 2.7×（18.9 vs 50.3）——"溢出感"的实体是 spec 管线每步慢速访存/扫描类开销，非 KV 进内存（A5 已无 offload 通道）。T-perf 任务靶子升级入计划 §5.5；A5 锚按现状锁定（迁移零容差对着现状，优化后另行更新锚）。下一步：cp312 venv + 底座 git 化（阶段 0 剩余）。

## 步骤 006 — decode 性能疑云排查（2026-09-25 深夜，插曲收档：引擎零回退）

- **协议**：用户质疑长上下文锚点的 decode 速率低得离谱（"真跑起来起码 80 tok/s"），假设 KV 溢出到内存。判据：找出低值真因 + 用原口径复测历史基线（doc_4k N=3，历史 85.18 tok/s），若回退则立任务留到移植后优化。
- **操作与证据链**（四步定责）：
  1. **排除溢出**：`kv_offload` 计数器 CPU→GPU = **0 字节**（全程无 KV 从内存读回；GPU→CPU 11.7GB 全是 prefix store 写出，lookup 同步延迟合计 66µs）。用引擎自报口径核对池值后做 A/B：无 offload/无 prefix-cache（池 1e9、16k ctx）4k/8k = 58.8/59.2 vs 有 offload（N2 原配方）61.4/60.5 —— **短上下文两组持平，offload 不背锅**。
  2. **测量 bug（主因之一）**：vLLM 流式每引擎步一个 delta、可含多 token，我按 chunk 数当 token 数算稳态——早前"22/14/7/6.5"实为**步/秒**，真值 ≈×2.1。已改按 `usage.completion_tokens` 计。
  3. **配置变量（主因之二）**：现部署是 **N=2**（spec-tokens 2，今天 rollout 拍板），同配置历史锚 = 60.65 median；我们 N=2 测得 60.5-61.4 **完全吻合**。N=3 复测（热身+3 重复）4k 中位 64.8（峰值 72）——与 85 的剩余差 = 我的合成 haystack（三段拼接+问答）接受率仅 0.53-0.57，历史口径 doc_4k 单文档续写接受率 0.65-0.74。
  4. **原口径终判**：runner v2 `--exp V1`（cell4 doc_4k，3 冷启动 × 5 样本，与历史 85.18 同协议同 launcher）→ **82.28 / 88.92 / 83.33，中位 83.33 tok/s**。
- **结果**：历史 85.18 复现于 83.33（±2%），**引擎零回退**；性能优化任务**不立**（用户条件：真降才立）。热身缺口已修（`--warmup 1 --repeats 3`，runner 口径弃 1 取中位）；16k 档 40-43 tok/s 为长度效应非异常。
- **判定**：插曲收档。**新增常备纪律：实验/锚点配置禁止 KV 溢出内存**（池值手算贴合上下文上限、测量组不用 offload/prefix-cache 把 KV 赶去内存；生产配方的 offload 用途不变）。A5 长上下文锚按最终脚本（热身+重复+真 token 口径）重采。

## 步骤 005 — A1 PPL 逐位主锚落盘（2026-09-25，阶段 0 首项）

- **协议**：迁移等价性判据的根。固定 prompt 集 = `_spec_eval_prompts` 标准族 8 条（code/doc/reason × 4k/16k/48k），裸 content 不过 chat template（隔离权重/量化路径数值，跨栈稳定）；mean_nll = −Σlogprob/n（prompt_logprobs=0 取实际 token），六位小数逐位比。运行口径对齐生产 N2 配方：eager + **nvfp4 KV** + `language_model_only` + `max_num_batched_tokens=1024`（覆盖 48k prompt 的 KV 预算）。新栈复跑必须 meta 同参 + prompt_sha256/tokenizer_sha256 同值才可比。
- **操作**：写 `tools/anchor_ppl.py`（采集器）+ `tools/run_anchor_ppl.cmd`（VS 环境 + 生产环境契约包装，CRLF）。**四跑三坑的调试链（按调用栈逐层定位，非 grep 散点）**：
  1. 跑①：humming JIT `filter_cuda_paths` 抛 "No suitable CUDA 13 environment" → 缺 `CUDA_HOME`，须用生产约定 `C:\PROGRA~1\NVIDIA~2\CUDA\v13.3`（**8.3 短路径 + 反斜杠**）；
  2. 跑②：`humming/utils/nvrtc.py:91` 构建 NVRTC 辅助工具时 `CreateProcess` WinError 2 → 该工具用 **cl（MSVC）** 编译，且 humming 缓存键含 CUDA 路径签名 + HOME（生产 HOME=`C:\fi`，缓存在 `C:\fi\.humming\`）——我 shell 里 HOME/斜杠不同必缓存 miss → 重建 → 无 cl 崩；
  3. 跑③：同病灶换位置——torch `cpp_extension` 用 **cl+ninja** 现场编 `humming_launcher`，`where cl` 失败 → **必须在 VS vcvars64 环境里跑**（本机 BuildTools 2022），故落 `run_anchor_ppl.cmd` 包装；
  4. 跑④：编译通过、模型 10.49 GiB 加载完成，卡 KV 预算——eager+bf16 KV 下 57344 需 3.68 GiB 仅剩 0.69 GiB → 按生产配方切 nvfp4 KV + lang_only + batched 1024 → 3.07 GiB 余量、**152,917 tokens 池**，8 条全绿。
- **结果**（158.8s 全程，`docs/锚点数据包/ppl_anchor_overlay0271.json`）：

  | doc_4k | 4,070 | **2.436307** | 11.430749 |
  | reason_4k | 4,038 | **1.106345** | 3.023287 |
  | code_16k | 16,322 | **1.032311** | 2.807548 |
  | doc_16k | 16,236 | **2.440256** | 11.475973 |

  引擎侧观察：decode 走 **XQA (SM120)**、nvfp4 KV 写入 = FlashInfer CUDA writer、HummingLinearKernel 承担 WNA16 int3；引擎提示可用 `--kv-cache-memory=3136590087` 替代 utilization（手动池值铁律的引擎自报口径）。
- **判定**：A1 主锚 ✅ 落盘，新栈复跑口径已固化（meta + 双 sha256 校验）。「跑 vllm 必须 VS 环境 + 生产环境契约」已成文（`run_anchor_ppl.cmd` 即合同），迁移期所有离线脚本一律走此包装。下一步：A5 204k offload 配方锚。
