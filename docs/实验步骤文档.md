## 步骤 036 — 改分组落地（`VLLM_KV_GROUP_SIZE` 开关）：容量 +18.5%、max_model_len 110k→140k、草稿 KV 窗口化定罪（2026-09-28）

- **协议**：接 035 定罪「L=5 是取整最差点，改分组是唯一免费容量来源」。四问：①**容量**——G 表必须与公式逐点吻合（口径 = 引擎自报 `GPU KV cache size`）；②**正确性**——needle 多深度 + PPL（数值等价）；③**性能**——decode 步长与 prefill 不得回归（时间对称交替 A/B）；④**提长**——`--max-model-len` 上限从 110,000 能推到多少、推上去是否真的可用。形式要求：**默认行为零改动、可一键回退**（不破坏上游对其它混合模型的行为）。另：用户中途提问「草稿模型占用随上下文增长而非滑动窗口有没有修复」——须以**直接测量**回答，不得用推算。
- **操作**：
  1. **读透机制**（`vllm/v1/core/kv_cache_utils.py`）：`_get_kv_cache_groups_uniform_page_size` 的 `group_size = min(各桶层数)`（1.5 启发式兜底）；`_get_kv_cache_bytes_per_block` 取 `max over groups(Σ page_size_bytes)`；`get_kv_cache_config_from_groups` 用 `num_blocks = available // bytes_per_block` 让所有组共享同一 num_blocks；`_max_memory_usage_bytes_from_groups` 的每请求块数 = `Σ_g cdiv(spec.max_memory_usage_bytes, spec.page_size_bytes)`。
  2. **写补丁** `tools/apply_kv_group_size_patch.py`：只加一个 env 开关 `VLLM_KV_GROUP_SIZE=N`（设置则强制 group_size，不设置走原分支、逐字节不变）；apply/revert 幂等、同时覆盖底座仓与 venv、带换行符与锚点计数断言。
  3. **写实验工具**：`make_kvgroup_launcher.py`（容量探针，PYTHONPATH 换 kvdump shim）、`make_kvgroup_len_launcher.py`（**保留 pin_shim 的生产孪生** + 改 max_model_len）、`kvgroup_boot.ps1`（G 表扫描）、`kvgroup_needle.ps1`（needle 门）、`kvgroup_perf_ab.ps1`（性能门，同 boot 内既测 decode 步长又测 prefill）、`make_ppl_kvgroup.py`。
  4. **扩展 kvdump shim**：逐组打印 `blocks/request`（`cdiv(max_memory_usage_bytes, page_size_bytes)`），把「某组领多少块」从算术反推变成实测。
  5. 跑 G 表（G=1/2/4/5/8/16，pool 3.4e9、max_model_len 110,000）→ 选 G → needle 门（@110k 四档；@140k 三档）→ PPL 门（基线重跑 ×2 + G=8 ×2）→ 性能门（P/G8 时间对称交替 6 臂 + prefill 4 臂）。
- **结果**：
  - **机制（kvdump 实测校准）**：`unify_kv_cache_spec_page_size` 把 mamba/full/sliding-window 三种 spec 的每层 page 统一到同一个值 **3,262,464 B = 2832 token × 1152 B/token**（block_size 2832 由 `_align_hybrid_block_size` 对齐 mamba page 得到）。于是 ①`bytes_per_block = (组内最大层数) × 3,262,464`，随 group_size 线性增长；②每组的 `blocks/request` **与组内层数无关**（full 组恒 `cdiv(max_model_len, 2832)`、mamba 组恒为 align 份数、sw 组恒为窗口块数）⇒ **`blocks_per_request` 只取决于各桶被切成几组**。
  - **G 表（实测 6/6 与公式逐点吻合）**：pool 3.4e9、max_model_len 110,000 下 `capacity = ⌊pool / (G×3,262,464)⌋ / [39·cdiv(16,G) + 4·cdiv(48,G) + 3·cdiv(5,G)] × 110,000`：

    | G | bytes_per_block | num_blocks | 组数 | blocks/req | 容量（预测/实测） |
    |---|---|---|---|---|---|
    | 1 | 3,262,464 | 1042 | 69 | 831 | 137,930 / **137,930** |
    | 2 | 6,524,928 | 521 | 35 | 417 | 137,434 / **137,434** |
    | 4 | 13,049,856 | 260 | 18 | 210 | 136,190 / **136,190** |
    | 5（上游） | 16,312,320 | 208 | 15 | 199 | 114,974 / **114,974** |
    | 8 | 26,099,712 | 130 | 9 | 105 | 136,190 / **136,190** |
    | 16 | 52,199,424 | 65 | 5 | 54 | 132,407 / **132,407** |

    **选 G=8**：容量与 G=4 并列 136,190（比 G=1 只低 1.3%），但组数 **9**（比上游 15 还少 6，比 G=4 少 9），boot 也最快（62-69s）。
  - **草稿 KV 窗口化——直接实测**（回答用户提问）：kvdump 逐组块数显示，草稿的 sliding-window 组 **恒为 3 blocks/request**（`max_mem = 9,787,392 = 3×3,262,464`，即 8,496 token 的空间），而 target 的 full 组随 max_model_len 变化：**39 blocks @110k → 50 blocks @140k**；mamba 组恒 4 blocks。**草稿占用是窗口常数，不随上下文增长**。034 的「草稿 27%」是「有草稿 vs 无草稿同池容量差」的混合量，主因不是草稿 KV 字节，而是它的 5 层把 `group_size` 从 16 压到 5 ⇒ target 16 层 full 从 1 组变 4 组（39→156 blocks/请求）——**这正是本步改分组修掉的东西**。
  - **needle 门**：G=8 @110,000（8k/32k/64k/100k）四档全中（ttft 4.75/20.43/35.48/52.51s，稳态 104.8-119.6 tok/s）；G=8 @**140,000**（8k/64k/**130k**）三档全中（ttft 5.27/47.13/**87.66s**，稳态 104.7-120.4 tok/s）⇒ **140k 上下文可用**。
  - **提长能力**：G=8 时 `num_blocks=130`、`blocks_per_req(L) = 2·cdiv(L,2832) + 27` ⇒ `cdiv ≤ 51.5` ⇒ **max_model_len 上限 ≈ 144,432**；实测 140,000 → 引擎自报 **143,307 token**（预测 130/127×140,000 = 143,307，精确）。当前生产是 110,000（容量 136,190 用不满）。
  - **性能门（时间对称交替，同 boot 内测 decode + prefill）**：decode 步长 **P 18.73 / 18.74 ms vs G8 18.30 / 18.31 / 18.32 ms ⇒ G=8 快 0.43ms（−2.3%）**，steady 129.9-130.4 vs 130.8-133.0 tok/s，acc 无系统差异（P 0.7225/0.7438 vs G8 0.7013/0.699/0.718）；prefill 64k 冷档（只命中 8k，新增 56,626 token）**P 47.263 / 47.248 s vs G8 47.171 / 47.171 s ⇒ 无差异（−0.18%）**。**P#1 的 32.61ms 是快慢态孤例**（第一个臂、紧跟 PPL 门之后），后续 P 臂回到 18.73/18.74，与生产水位 18.55ms 同带。
  - **长稳（生产配置 20 条混合请求）**：**20/20 全部健康**（`status=OK`、`error=None`、无 HANG、`health_after=True`）—— 脚本按 `n_tokens>500` 阈值报的 5 个 FAIL（`decode2k_1/2`、`wiki8k/32k`、`wiki8k_repeat`）**全是假阳性**：全部 `finish_reason="stop"`（模型自然结束，n_tokens 79-118），即挂账的「`n_tokens>500` 阈值误判早停」代码债（第四次）。关键指标正常：step_p50 **18.15-19.22 ms**（与性能门的 18.30 同带）、wiki 类 accept_rate **0.74-0.80**、needle 8k/32k/100k 全中（100k ttft 75.23s、稳态 113.9 tok/s）、多轮 TTFT 8k 4.55→2.96s / 32k 20.38→2.97s、reasoning（reasoning_len 746）与 tool-call（finish=tool_calls、args_ok）正常。
  - **生产冒烟**（`serve_gsq_prod029_n2.cmd` 落地 G=8 + `--max-model-len 130000` 后）：引擎自报 **142,016 tokens / 1.09x**（预测 `⌊130/119⌋×130,000 = 142,016`，精确）、`layers-per-group 5 -> 8` 生效、needle 8k/32k 全中。

  - **PPL 门——判据本身被推翻**：基线（不设 G）重跑两次与历史锚 `ppl_anchor_base029_lineBfix_r5.json` **不逐位相同**，且**同配置两次 boot 之间的漂移（最大 +2.01e-03）≥ G=8 与基线的差异（最大 1.4e-3）**，漂移无系统方向（相对差 ≤0.32%）。⇒ ①**PPL 在本栈上不是位精确的**（每次 boot 都随机漂移），「PPL 逐位」这条判据在 0.29 栈上**不成立**，未来必须改为容差判据（`|Δmean_nll| < 3e-3` 量级）+ 多采样；②G=8 与基线**无系统差异信号**（落在同一漂移带内）。正确性主判据改为 needle 多深度。
  - **同 64k 档「@110k 35.5s vs @140k 47.1s」的疑点已澄清**：不是提长代价，而是 **prefix cache 命中量不同**——档位序列 `8k→32k→64k→100k` 时 64k 档命中前 32k，序列 `8k→64k` 时只命中前 8k；本次 A/B 用同一序列（`8k→64k`）两臂都 47.2s，与 PPL 门的冷 prefill 1,378 tok/s 同量级。
- **判定**：
  - **改分组落地成功**：env 开关形式（默认零影响、`tools/apply_kv_group_size_patch.py revert` 一键回退，底座仓 commit `f0bff05`），G=8 把池 3.4e9 的容量从 **114,974 提到 136,190（+18.5%）**，`--max-model-len` 上限从 110,000 提到 **≈144,432**（实测 140,000 可用、130k needle 命中），**池大小与溢出量一个字不变**；decode 反而快 2.3%（组数 15→9），prefill 无差异。
