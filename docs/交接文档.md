### 1.3 容量线（已到头）

**池值 3.4e9 是硬上限**（035 定罪：同长度 101,166 token 对照，3.4e9 冷 prefill 92.25/92.33 s vs 4.6e9 382.78/379.95 s ⇒ 池值本身让 prefill 慢 4.13×；3.8e9 一半概率崩）。**唯一免费来源 = 改分组**：`VLLM_KV_GROUP_SIZE=8` 把 layers-per-group 从上游启发式的 5 强制到 8 ⇒ 容量 +18.5%、组数 15→9、decode 还快 2.3%（036）。**提长**：`--max-model-len` 110,000 → 130,000 → 140,000（039）→ 144,432（040）→ **163,072（046 定稿，ssm bf16 后 G=8 新硬上限 `2·cdiv(L,1456)+28 ≤ 252`，容量 163,719）**。

**容量公式定版**：`blocks_per_req = cdiv(L,2832)×cdiv(16,G) + (2+N)×cdiv(48,G) + sw×cdiv(5,G)`，约束 **`≤ num_blocks − 1`**（引擎在准入检查前永久扣一个 null block，`check_memory = available_memory - bytes_per_block`），其中 `num_blocks = ⌊池/(G×3,262,464)⌋`、**`sw = cdiv(2047 + 2×mbt, 2832) + 1`**（本栈 `max_concurrent_batches = 2`）⇒ **mbt 与容量耦合**。

**⭐容量线结案（步骤 047/048，2026-09-28）**：两条新路径**双 NO-GO** —— ①**1bit 草稿权重全族不可行（047）**：推理端四道门全否（`INCConfig.SUPPORTED_BITS={2,3,4,5,6,7,8}` / `CUDA_HUMMING_SUPPORTED_BITS={2,3,5,6,7}` / humming csrc 的 layout+TMA 按 4/8bit 写死 / auto-round pack 只覆盖 2/3/4/8），实测 `INCConfig(bits=1)` → `ValueError` ⇒ mlp 1bit（−171 MiB）与 o_proj/kernel_proj 1bit（−22 MiB）作废、激进档 190,736 作废。②**E 轨（池值守恒回填 3.4e9→3.686e9 + L 163,072→177,632）容量 +9.3% 达成（178,938 tokens）但长档冷 prefill −18.6%（048）**：160k 冷档 A 909/919 vs E 轨 727/761 tok/s。**归因实验（臂 D：池值同 3.686e9 + L 保持 163,072 → 907 tok/s ≈ 基线 914）证明代价来自 `max-model-len` 而非池值** ⇒ 调研档「守恒回填在机制上避开 035 触发条件」被否定，**且任何以抬高 max-model-len 换容量的路线都带此代价**（机制挂账，扩展 039 的「max-model-len 敏感」观测）。**唯一剩余杠杆 = 码本 4→2bit**（−30 MiB ⇒ L 180,544，+1.6%；技术已核可行：`_dequant_gather_kernel` 的 `NUM_BITS`/`PACK_FACTOR` 是 triton constexpr、docstring 明示 2-8bit；风险 = 码本质量打接受率）。

### 1.5 ⭐新线：KVMem 虚拟化 KV 工作区（步骤 056 立项，**设计定稿、未开工**）

**设计唯一权威 = `docs/vllm-030win-调研-KVMem虚拟化KV工作区.md`**（含四轮决策记录、参考实现缺陷取证与规避映射表、参数标定、阶段出口、验证台口径、风险登记册）。本节只是入口摘要，**不要据此施工，施工前读全文**。

**目标能力**：①（主）**接受超长 transcript** —— 客户端照旧发全量，服务端把超过视窗的历史 KV 分页到 host，GPU 只保留有界视窗，工作区上限 **262,144 token**；②（副产品）免客户端压缩、免全量重 prefill；③（结构收益）**上下文长度与 GPU 池解耦** ⇒ 缩池可换显存余量（直接对冲 049 悬崖）。**明确非目标 = 长上下文召回**（论文作者本人建议 `-c` ≤ 200k；其定位是 agent 长程任务）。

**⭐核心架构 = (C) 固定槽位布局**：布局 `[sink S | 检索槽 N | recent R | query q | 生成预留 g]`，槽位位置在请求开始前由确定性规则算出。**关键不变式：query 位置 `B = S+N+R` 与"最终选了哪些块"无关**（N 固定，选择只决定槽内容）⇒ 一次消掉三个问题：①**不需要重 prefill** ⇒ GDN 每步只前进一次 ⇒ **不需要 GDN 状态快照/恢复**；②**视窗稠密连续** ⇒ **不需要 mask** ⇒ 生产注意力路径（nvfp4 flashinfer + FULL_AND_PIECEWISE）一行不动；③**不存在 "query replay" 概念** ⇒ 参考实现 #43/#13 的"跳过 replay → 全量重 prefill 136 秒"退化路径**结构性不存在**。

**三条硬约束（决定一切）**：①**块粒度 1456 token**（混合模型页对齐强制，改小到 128 会让容量掉约 11×）⇒ 检索索引用 128-token 子块、搬运按整页；②**GDN 循环状态不能回退**（`num_prefill_checkpoint_blocks = 0`、单条前进状态）⇒ 这是选 (C) 的直接原因；③**显存余量悬崖**（049/055：池后任何新分配 64 MiB 即 8k 解码 121→85 且不回弹；参考自己的 capture staging 默认 448 MB pinned + 448 MB 显存）⇒ **新增显存必须池前分配并从池预算扣出，预算 192 MiB**。

**host 预算**（用户 2026-09-29 裁定：**offload 可缩到 2G/1G，不用管 NVMe**）：工作区 262,144 的全量 KV = 4.83 GiB；实际 host 需求约 **3.7 GiB**（溢写 V + 位置无关 192 维 K ≈ 1.5 GiB + raw K 权威 fp16 只存旋转 64 维 = 2.1 GiB + 索引 67 MiB）⇒ **不需要 NVMe**。

**为什么不用参考的路线**：参考走"原始位置 + 洞 + KQ mask"（v0.3.0 明写"**禁止 pack `[0..W)`**"、架构文档写"**no unrotated raw-K and no re-RoPE on the product path**"），但 **vLLM 的 mask 路径只支持 fp16/bf16 KV**（`FlexAttentionBackend.supported_kv_cache_dtypes = ["auto","float16","bfloat16"]`）而生产 KV 是 nvfp4 ⇒ 改 flex 要么视窗缩到 ~48K（对 ≤163K 的 prompt 反而退化）、要么给 nvfp4 新写 mask/稀疏 kernel（动全栈最脆弱处）。论文/QW3 的"重 prefill query"路线也被否（要 GDN 快照 + 带 #43 同族退化路径）。

**参考实现已暴露缺陷（open 未修）与我们的规避**（取证详见调研档 §4）：**#43**（`query_replay_fits()` 按策略预算而非物理池判定 ⇒ replay 跳过 + 丢掉紧贴 query 的工具输出 + 83,909 token 全量重 prefill 136 s）→ **(C) 无 replay ⇒ 免疫**；**#4**（>210K 中段**串台**，报告者归因量化副本上反复 delta re-RoPE 累积误差）→ **我们每次入槽一律从 raw K 单次重建 ⇒ 零漂移**（"8 次 remap/累计位移阈值"那套参数作废）；**#56**（全量重发下 prompt+gen > 池 ⇒ CUDA OOM 杀服，守卫只查 `n_ctx`）→ **冷启动 prefill 期 stage-out 列为阶段 1 独立子里程碑 1a**；**#55**（staging 448 MB 高水位）→ 192 MiB 池前分配；**#34**（prefill 单 token 成本 ∝ 视窗，**但缩小视窗不伤检索质量**）→ 缩池是双赢；**#22/#82**（Windows 多轮 agent 12-20 tok/s）→ **参考性能不可作我们的锚**。

**阶段划分**：**1a 冷启动 prefill 期 stage-out（独立子里程碑，必须先做）** → **1 正确性打通**（文本 + 无投机 + 无图模式 + 池值不动 3.4e9；出口 = identity canary + 紧预算 needle 对照 + 262K transcript 跑通 + 163K needle 多深度不退化 + 重物化往返单测）→ **2 性能**（融合 kernel 捕获、GPU 打分调参、重 RoPE 批量化）→ **3 叠生产特性 + 缩池治悬崖**（DFlash2 投机、图模式、把 96K 压力配置正式化）。

**参数速查**：主配置 视窗 163,072 / 生成预留 32,768 / sink 1,456（1 页）/ recent **动态 = 最近一次工具输出长度 clamp [16K, 64K]** / 检索余量约 65-113K（留取率 62%，**弱信号**）；**96K 压力配置** = 视窗 98,304 / 生成 32,768 / recent 32,768 / 检索 ~31K（**留取率 21%，检索变刚需**）；budget 下界 = sink + recent + ≥16K 检索（约 96K）；工作区能力上限 262,144，**200K-262K 标"已知风险带"只记录不判死**、阶段 1 闸门 ≤200K。

**量级与交付形态**：**3-6 周**；引擎侧风险低于预期（参考的引擎补丁仅 **+182/−15 行、三张、未改 FA kernel**，工作量大头在 adapter/连接器与 kernel）；全程**变体 bat 并存、生产默认不动**。

## 5. 归因修正存档（防重蹈）

1. **「Marlin 分叉」撤销**：0.27/0.29 的内核清单顺序与 Marlin 位宽表（uint4b8/uint8b128/fp8/fp4）逐字相同——0.27 生产同样由 Marlin 接 int4 embed/lm_head，**非迁移差异**；「旧栈全线 Humming」是对步骤 010 单条日志的过度概括。
2. **S6 的 eager 21.x vs 43 归因作废**：口径混杂（单发续写 vs runner 3×5 median）+ fp8/nvfp4 KV 读带宽差都可能贡献；批 4/5 后用 runner v2 口径重测再谈。
3. 0.29 的 reasoning 字段名 = `message.reasoning`（非 reasoning_content）；GSQ chat_template 硬编码 "Reasoning effort xhigh" system 提示——thinking 发散/答非所问归模型+模板，非引擎（S2/S14 PPL 已锁前向等价）。
4. **「PPL 逐位判等」撤销（步骤 036）**：同配置两次 boot 的 mean_nll 就差 **1e-3 量级**（最大 2.01e-03、无系统方向）⇒ 本栈不成立；正确性主判据改用 **needle 多深度**，PPL 改容差 + 多采样。根因待挖（nvfp4 KV / flashinfer autotune 嫌疑，后者已被 `#54794` 的实测空缓存排除）。
5. **「144k 悬崖」撤销（步骤 040）**：039 把 144,432 的 decode −21% 读成 `max_model_len` 效应，交替 boot 复测证明是**随机慢 boot**（同一 L 两次 boot 118-121 vs 96-99，慢的那次专用显存**反而少 284 MiB**，`pin_shim` 放置日志 **15 次 boot 逐字节相同**）。**教训：提长/降投机类改动必须多 boot 交替，单轮会把 boot 方差误判成配置效应。**
6. **「031 的 idle 8ms」撤销（步骤 033）**：那是带 stack profiler 自身开销的假象；轻量 profiler 下 GPU busy 20.03ms/93.9%、idle 仅 1.30ms。
7. **「FULL 图必挂死」部分撤销（步骤 026）**：显式 PIECEWISE 禁 FULL 图；**默认 FULL_AND_PIECEWISE 下 decode FULL 整图验证安全**（三段捕获全过、长稳 20/20），已是生产配置。
