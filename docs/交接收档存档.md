## 步骤 065（2026-09-30）— KVMem K3 后半接线第二半：**`PageGeometry` 内核块重写 + 实时重物化往返 GO**（量化步内一致）

用户指令「读交接提示词，继续推进」。按 064 判定的修复路径走完第二半：①`PageGeometry` 换内核块公式；②**同步改离线单测的页构造**（064 定性为自证陷阱）；③重跑实时往返（判据 = 逐位或量化步内一致）。

**落点**：`remat.py`（`PageGeometry` 加 `kernel_block_size`、`chunks_per_page`/`chunk_bytes`/`side_chunk_bytes` 属性、`rotated_byte_offsets` 换 §12.10.3 公式、`__post_init__` 加整除断言）；`worker.py`（注册时从真实 cache 张量推 kbs：`ratio = cache.shape[0] // num_blocks`，断言整除；注册日志补打 `89 chunks x 18432 B, kernel block 16`；自检精度契约修复；报告加 `max_e2m1_step`/`delta_over_step`；dump 数组转 fp32）；`tools/kvmem_remat_test.py`（T0 加 chunk 常量断言、T2 物理 buffer 重写为真实布局 + 内核块粒度幻象视图 + "只碰页 0"断言、T3 carve 复推改从同一视图出发 ⇒ **25/25**）；臂 dump 目录 `kvmem_k3e → kvmem_k3f`（064 证据零覆盖）。

**结果**：①**离线 25/25**：真实布局下引擎 writer 与 primitive 偏移公式**逐位一致**（205,056 字节 0 mismatch）、carve 独立复推全等、整页重建逐位一致、slot→kernel block 不串页。②**实时往返第一轮（r1）**：布局修复生效——**nan 从 44.6% → 0**、max_byte_diff 255 → 128——但仍有 ~2% 字节差、delta 1.5-2.0（超步）。③**离线定位**：差异均匀分布于全部 token/chunk/head（排除布局/边界）、全为邻档翻码；根因 = **精度契约**——fp16 权威行直喂 bake 且 cos/sin 被截到 fp16，而引擎 triton kernel 是 **bf16 K × fp32 cos/sin**，双重舍入 ⇒ amax 抖动翻码。离线验证：fp16-as-fed 差 1.92% ⇒ **还原 bf16 后 0.506%**、dequant 误差 **max 0.5625 步长、0/364,544 超步、0 非有限**。④**修复后实时往返（r2，第三次 boot）**：8 页 × 16 层全部重建，字节差率 **0.41-0.56%**、**`delta_over_step` = 0.0068-0.127 全部 ≤ 1 步**、**nan = 0**、`rows_written = 2,659,328`、`unmapped/missing = 0`；检索侧未回归（`dot@64` rank 2）。⑤**运维**：dump 目录在第一次误启后即改 `kvmem_k3f`（064 的 k3e 证据零覆盖）；r1 失败态证据改名 `_r1_fp16asis` 保留；生产 watchdog 恢复。

**⭐新纪律（进必守 16 的 065 补充）**：①**精度契约**——权威区 fp16 无损存 bf16，但重建必须 `raw.to(bfloat16)` + fp32 cos/sin 再走引擎同款计算，违反则双重舍入翻码超步；②**实时往返达标形态 = 量化步内一致**（残余 = triton 与 host 复算的 fp32 舍入序列差，不可归零也无需归零）；③**`np.savez` 不支持 BFloat16**（诊断数组转 fp32，否则 EngineCore 崩）；④复跑前改 `VLLM_KVMEM_DUMP` 目录，失败态证据改名保留。

**判定**：**实时重物化往返 GO**——"存 raw、重建页"在字节级成立（量化步内）。**未验证（勿当成已验）**：①往返自检只测"原位重建"，**窗外 needle 仍答不出**；②位置解耦（`gpu_model_runner.py` 的 positions，先改位置后算 slot）+ 块表改写（flashinfer 路径无 `update_block_table` ⇒ 要动模型执行器）未开工；③固定槽位 0..B-1 的真实装配未测；④不判性能（阶段 1 判据不含）。

## 步骤 064（2026-09-30）— KVMem K3 后半接线第一半：raw-K 权威区落地 + **实时重物化往返自检抓出页布局假设错误**（根因查清）

用户指令「读交接提示词，继续推进」（前半会话已交付 063）。按 063 判定的接线顺序做第一半：**存储格式 = 工作区页保持整页原样 + 独立的 pre-RoPE 旋转前缀权威区**，并在工作区自检里加**实时"重烘焙往返"**。**为什么不用设计档 §5.3 的"槽内拆分存储"**：①拆分把每逻辑页从 25.03 MiB 涨到 33.02 MiB ⇒ 122 槽 = 4,028 MiB **超出** 3,072 MiB 预算，而独立权威区（旋转 64 维 fp16，512 B/token/层）对全 262,144 token 只要 **2.0 GiB**；②K1 的整页 memcpy 与往返自检语义原样保留；③拆分要在 store 路径逐头重排（host ~26 MB/逻辑页），阶段 1 不判性能不值得先付。**副作用**：槽内旋转前缀的 nvfp4 字节成为死重（12.5%），重物化时总被覆盖，无正确性问题。**零注意力行为改变**：权威区只写只读、没有页被放回视窗 ⇒ 全部新行为在 `VLLM_KVMEM_AUTHORITY`（默认关）门控后 ⇒ 生产行为逐字节不变。

**落点**：`config.py` 三旋钮（`VLLM_KVMEM_AUTHORITY` / `_TOKENS` 默认 262,144 / `_TRAJ` 默认 2）；`worker.py` 层号↔层名映射 + 权威区分配/写入/读回 + `_run_remat_selftest`（实时往返）+ 报告 `kvmem_remat_selftest.json` 与数组转储 `kvmem_remat_arrays.npz`；launcher 3 行 env + dump 目录 `kvmem_k3e`（k3c/k3d 是 062 证据不覆盖）；离线单测加 T8（打包 K 切片外部锚）/ T9（权威区绝对偏移索引）⇒ **22/22**。

**结果（机制 GO）**：16 层全部映射（层号 3,7,…,63）、16 个区域、`authority_bytes = 2,147,483,648 = 2.0 GiB`（与设计 §3.4 的 2.1 GiB 吻合）、`rows_written = 2,659,328`、`unmapped = 0`、`missing = 0`；每层非零行 166,208（首 store job 时刻快照 ≈ 视窗边界）；K1 往返自检不受影响（`8 pages × 16 layers byte-identical`）；引擎侧 rotary 解析正确（`get_rope` 命中同一 `_ROPE_DICT` ⇒ 与模型同一 `MRotaryEmbedding` 实例：cache `(1048576,64)` fp32、rotary_dim 64、NeoX、interleaved）。

**⭐核心发现：实时往返失败 → 页布局假设被证伪**。8 页 × 16 层全部重建，**8/8 页字节不同**、`max_byte_diff = 255`、去量化差 **44.6% 非有限**（NaN/inf = 把 data 字节当 scale 读的特征）；差异**全在 K 侧**（V 侧 0 字节不同）；模式 = **token 0..15 的旋转数据完全一致、token 16 起整段不同**。**真实布局（数据区 15/15 探针精确命中 + 尺度区 58.84% vs 旧假设 0.93%）**：

```
页（1,640,448 B）= 89 个 18,432 B 的 chunk（89 = 1424/16；16 = 内核块 kbs）
chunk(t//16) = [K 侧 9,216 B | V 侧 9,216 B]
每侧 = [heads × kbs × 128 data (8,192 B)] 紧接 [heads × kbs × 16 scale (1,024 B)]
data 偏移  = (t//kbs)*18432 + side*9216 + h*2048 + (t%kbs)*128 + j
scale 偏移 = (t//kbs)*18432 + side*9216 + 8192 + h*256 + (t%kbs)*16 + k
```

即 **K/V 按 16-token 内核块交错**，**不是**"整块 K 侧 + 整块 V 侧、每侧内部 `[heads][1424]`"（`side_carve_views` 的假设——该公式对 **kbs-token 内核块**成立、对 **1424-token 管理块**不成立）。**为什么 063 的离线单测没抓到**：它验证的是"用引擎的参考 writer 写进**自己构造的视图**"——锚错了对象（**自证陷阱：两端都是自己写的**），与既有记忆《格式搬运必须有外锚》同构。**修法（已定，未实现）**：`kbs = spec.block_size // ref.shape[1]`（`ref = group_kernel_blocks(...)` = `cache.unflatten(0,(num_blocks,-1))`，本例 1424//89 = 16），把 `PageGeometry` 换成上式，并**同步改离线单测的页构造**。

**修掉一个真缺陷（本轮第一、二次 boot 暴露）**：capture 层键 = **整数层号**、工作区层键 = **层名字符串**，首版缺映射导致权威区**静默没写入**（自检一声不吭）。修法 = `extract_layer_index` 建映射 + 未映射计数/告警 + 报告补 `rows_written`/`authority_nonzero_rows`/`nan_elements` 等可核对量（**把静默改成响亮**）。

**判定**：**权威区机制 GO；重物化在真实页上未通过——但根因查清且修复路径明确；本步最大产出正是把"063 的离线 GO"证伪到"真实页不成立"**。若不修，任何"把工作区页放回视窗"的实现都会把错误偏移的 K 喂给模型（"检索选对了但读出来是糊的"，与检索问题不可区分）——063 判定预警的失败模式在真实页上复现并定罪。**未验证（勿当成已验）**：①真实布局的 `PageGeometry` 未实现；②离线单测未在真实布局上重建（需同步改页构造否则仍是自证）；③实时往返未通过；④位置解耦 + 块表改写未开工。

**运维**：生产恢复 `prod_watchdog.ps1` boot0/1/2 SLOW（median 93.23/93.15/95.27，全在 042 的 83-99 低带）→ **boot3 FAST（median 120.56，120.56/118.63/120.94）**，`prod_headroom_check.ps1` **98 MiB = OK**；磁盘 115 G 可用。**生产配置未变（046）**。

**踩坑**：①**自证陷阱**——布局类断言的锚必须是引擎的**真实张量**（`ref.shape`/真实页比对），不能是"writer 写进自造视图"；②**静默缺陷**——映射/键空间跨界的缺陷必须带**可核对量**（行数/非零行数）与告警，否则自检也会一声不吭；③插入文档小节**再次吞掉下一节标题**（063 的标题被 064 覆盖，`grep -n "^## 步骤"` 复核后补回）——必守第 6 条第三次显灵。

## 步骤 063（2026-09-30）— KVMem K3 后半开工：**重物化原语 + 往返单测**（18/18 全过，离线逐位锚定引擎自身代码）

用户指令「读交接提示词，继续推进」。头名 = **K3 后半固定槽位重物化**（位置解耦 + 重 RoPE + 块表改写，量级 3-6 周）；本步只做其中**最不可事后补救、且可完全离线验证**的一块 = **重物化原语**（设计 §5.3 的"重烘焙"、阶段 1 出口的"重物化往返单测"）。**为什么先做它**：①它是整条重物化的算法核心，错了就是"检索选对了但模型读出来是糊的"，而**这种错在端到端 needle 上表现为"检索无效"，与真正的检索问题不可区分**；②不需要动引擎 ⇒ 零生产风险；③设计档要求的本来就是**单测**。**纪律**：生产默认不动（本步**只新增文件、无任何调用者** ⇒ 引擎行为逐字节不变，因此**不需要门控**）；池值不动 3.4e9；**不启臂**（生产占 15,891/16,303 MiB，起 CUDA context 会撞余量悬崖 ⇒ 单测跑 **CPU**）。

**几何（从三处引擎源码对账，不从文档抄）**：`full_dim = head_size//2 + head_size//16 = 144`（`utils/torch_utils.py`）；每页 `[K_data | K_scale | V_data | V_scale]`、HND 物理序 `(blocks,2,heads,block,full_dim)`（`create_kv_caches_with_random_flash`）；每侧内部 `[heads][block][data]` 紧接 `[heads][block][scale]`、**不是逐行交错的 144 字节**（`reference_nvfp4.py:side_carve_views`）。⇒ **K 侧 729,088 + 91,136 = 820,224 B、整页 `2×4×1424×144 = 1,640,448 B`**，与工作区每槽字节数**逐字吻合**。

**⭐ 新查出的结构前提（设计档此前没写）**：`rotary_dim = 256 × 0.25 = 64 = 4 × 16`，**恰好落在 NVFP4 尺度组边界上** ⇒ 旋转前缀覆盖**恰好 4 个完整尺度组**、不存在跨组撕裂 ⇒ **可以只重写旋转前缀**（全页 205,056 B = **12.5%**），其余 192 维与整个 V **一字节不动**；同时**组的归约域不相交 ⇒ 只在旋转组算 amax 与算整行再取那 4 组逐位相同**。`rotary_dim % 16 != 0` 则方案不成立（已写成硬断言）。

**RoPE 约定的两个反直觉点（按模型实际路径查）**：模型用 **`MRotaryEmbedding`**（`mrope_interleaved=True`、section `[11,11,10]`、NeoX），cache `[1,048,576, 64]`——①**cache 宽度 = `rotary_dim` 而非 `2×`**（cos 前 32、sin 后 32）；②`uses_mrope=True`、位置是 **2D `[3,T]` 三行相同**（`Qwen3_5.get_mrope_input_positions`）⇒ 引擎走 `triton_mrope`，但**三行相同使 `apply_interleaved_rope` 成为恒等** ⇒ **文本输入下 2D 与 1D 逐位等价**（实测 max|Δ| = 0）。**实现上不复刻公式**：旋转直接调引擎的 `ApplyRotaryEmb.forward_static` + `apply_interleaved_rope`，量化复用 `reference_nvfp4._e2m1_codes`（`k_scale = 1.0`，`attention.py:141`）。

**落点**：`v1/kvmem_workspace/remat.py`（`PageGeometry` / `rotated_byte_offsets` / `bake_rotated_k` / `quantize_rotated` + `dequantize_rotated` / `write_rotated` + `read_rotated` / `rematerialize_page`）+ `tools/kvmem_remat_test.py`（离线单测）。**测试设计原则 = 每一条断言都锚在引擎自己的代码上，不锚在原语身上**：旋转锚 = **逐行移植生产 `_triton_mrope_forward` 内核**，字节锚 = 引擎自己的 `write_reference_nvfp4_cache`，偏移锚 = 引擎自己的 `side_carve_views`（同一次落位两套独立算术各推一遍）；并加**反平凡**断言（位移必须真的改页面、不等行 M-RoPE 必须真的在置换）。

**结果（18/18，CPU）**：①几何 2/2；②**旋转 vs triton 内核移植 4/4，max|Δ| 全部 `0.000e+00`（逐位）**，且不等行与文本结果差 `3.457e-01` ⇒ 置换在动、移植非恒等式；③**字节 vs 引擎 writer：205,056 字节 0 mismatch**，其余 **1,435,392 字节全零未动**；④偏移经 `side_carve_views` 独立复推 3/3（data `(1424,4,32)` / scale `(1424,4,4)`）；⑤**位移 d=4096 后搬回原位逐位一致**（该位移确实改了 147,975 字节）、**连续 8 次位移后搬回仍逐位一致**；⑥量化误差 `2.734e-02` vs 最大 E2M1 步长 `7.813e-02`（**比值 0.35**）；⑦对引擎写的整页重烘焙后非旋转 1,435,392 字节**一个未变**；⑧**以 pre-RoPE 旋转前缀为唯一输入重建整页 == 引擎整页，逐位一致**。

**判定**：**重物化原语 GO（离线逐位钉死）**。设计出口要的是"量化步内一致"，实测给的是**逐位一致**；"一律从 raw 单次重建、禁 delta re-RoPE ⇒ 零漂移"从设计陈述变成**可执行断言**（参考实现 #4 的 >210K 串台机制结构性不存在，现在有单测背书）。**未验证（勿当成已验）**：①**引擎接线完全未做**（位置解耦 + 块表改写 + 存储格式改成"V+非旋转 192 维原样 / 旋转 64 维 fp16 权威"）⇒ 窗外 needle 仍答不出；②**单测跑在 CPU**——对过的是 triton 内核的**公式**（逐行移植），**不是它的实际执行**（fp 舍入未对；停服后可 `--device cuda` 补跑）；③**"工作区页 == 块原始字节"是结构推断**（`1,640,448 = 2×4×1424×144` 且 `swap_blocks_batch` 搬整块），未在引擎里取证；④未重跑栈内 `research/src/nvfp4_writer_swap_probe.py` 那条"writer 输出 == 真实 GPU 页字节"的既有证据。

**下一步（接线顺序建议）**：①**先落地存储格式 + raw-K 权威区**（容量账见设计 §3.4：溢写部分 V+非旋转 192 维 ≈1.5 GiB、旋转 64 维 fp16 权威 2.1 GiB、索引 67 MiB）并在工作区自检里加"**重烘焙往返**"一项——**这一步不改变注意力行为**，可以先把臂跑起来验证；②**再动 `gpu_model_runner.py` 的 `positions` 与块表**（这一步一开始就必须跑臂 + 双 boot，必守第 17 条）。

**本步零运维**：未启臂、未停服、未改生产配置（046 未变）；新模块无调用者 ⇒ 无 AOT 影响。

## 步骤 062（2026-09-30）— KVMem K3 后半第一步：残余早期页偏置**成因查清 + 危害量化 + 线性修法全否**（"背景与信号共享子空间"）

接手 061 的头号挂账（无针时页 2/5/1/11/8 就有 22.7–26.2 的页级 logit，把检索槽位占掉；061 已排除"页均值范数"，候选解释是"文档 3 单元循环 ⇒ 早期页更模板化"或"`k_norm` 学习权重在某些维度上系统性偏置"）。

**做了什么**：新增门控 **`VLLM_KVMEM_DUMP_KBAR`**（`config.py`），在 `index.py` 的打分路径里把排名所用的向量写进与报告同名的 sidecar `.npz`——**页级 mean-K**（新 `_layer_page_mean`：按真实页边界把子块和/计数分开累加再相除，**不是"均值的均值"**）、**子块级 mean-K + 计数**（`subblock_mean_k` / `subblock_counts`；**必须有**：引擎的页分是"页内子块取 max"，而针只占一页 1424 token 里的 15 个，页均值把它稀释 100 倍）、**query**（`q_group_mean` = 打分实际用的 head-group 均值）、**子块级与页级 logit**。**单测加外部锚**（`tools/kvmem_index_test.py`，合成数据真值）：页均值 K vs 喂入行 **9.4e-7**、q **0**、子块均值 **6.3e-6**、**离线重放页均值 logit 3.4e-8**。**探针加 `--question-preset off-topic`**（换问题的判别实验）。**新增 `tools/kvmem_k3_replay.py`**：离线**逐位重放引擎的 max 归约**（每个 query token 单独打分 → 页内子块 max → 层求和 → span 取均值，**顺序与引擎一致，因为 max 与 span 均值不可交换**），与引擎报告差 **3.3e-4**（fp16 量化级）⇒ 这是"离线结论 = 引擎结论"的外部锚。**两次采集**：k3c = 3 个 200K 请求（code control / **off-topic control** / needle d16），k3d = 2 个（control / needle d16，**带子块级分辨率**，sidecar 217 MB/次）。臂 = `tools/serve_gsq_kvmem_ws163k.cmd`（+`VLLM_KVMEM_DUMP_KBAR=1`，dump 目录 kvmem_k3c → kvmem_k3d），boot 数字与 060/061 逐字相同（`275,997 tokens / 1.05x @262,144`、`viewport needs 234 / pool has 259`）；单请求墙钟 ~274 s。

**成因（三条独立证据）**：①**偏置与 query 无关（决定性）**——同一文档、两个**语义无关**的问题（"访问码是多少" vs "哈希表怎么解决冲突"），页级 logit 的 **Pearson = +0.986**、mean|Δ| = 0.70、**top 页完全相同**；根因 = **两个 query 向量本身的 cos = +0.964（夹角仅 15°）**——query span 是"问题模板"的 8 次重复，模板的共同成分压过了语义差异 ⇒ **061 的"跨三次运行稳定"不是证据**（三次用的是同一个问题），也解释了随机 query 反事实为何 top 页分散（随机 query 没有这个共同成分）。②**方向 = k̄ 的第 2 主成分**：占 **22.2% 方差、与页偏移相关 +0.797**（正极端是后部页 132/138/137，负极端是前部页 7/1/2/0/6/8）；而 **query 与该方向的对齐 cos = −0.259，是随机基线的 49 倍**（随机 |cos| ~ 0.0053）。③**排除其他候选**：**16 层各自单独打分都给出同一批早期页**（不是某一层的偶然）；**top-8 维只携带 15.1% 的 logit 离散度**（排除"少数巨大维度 / `k_norm` 权重偏置"）；**页均值归约与 max 归约的 top-8 完全重叠**（排除归约方式）；范数恒定 ±4%（061 已排除）。

**危害（这才是要修的理由）**：针的实测 lift = **+6.48**（页 19：control 20.02 → needle 26.51，rank 8 → 1）。把同样大小的针**逐页放到每个候选页上**：**中位 rank 18、最差 71、59/116（51%）落在 top-16 之外**；前部三分之一中位 rank 1、后部三分之一中位 ~50 ⇒ **检索只在文档前 20% 有效**。配套：**针只在 max 归约下可见**（页均值归约下针页 rank 24/116，max 归约下 rank 1）⇒ §5.3 的"页内子块取 max"是**必需**而非可选。

**量级澄清**：位置偏置**只占 logit 方差的 15%**（corr −0.387，max 归约 / −0.735 页均值归约）⇒ r² = 0.15。**更根本的量级 = 97% 的页 logit 方差与 query 无关**（两个不同 query 的 r = 0.986 ⇒ query 相关方差仅 ~2.7%）。eligible 页 logit：中位 11.69、**std 5.38**、范围 3.47–26.27。

**修法全否（七类；一律用"该修法自身的真实 lift"评估——用 baseline 的 lift 会造出假改善）**：
- **去位置类**（q 投影掉 k̄ 对 offset 的回归斜率 β、子块线性去趋势、子块高通 w=2/8/32）：corr 从 −0.387 降到 **−0.011 ~ +0.047**，**真实针保持 rank 1**，但 **SNR 不变**（1.20 → 1.24~1.30），合成针中位只从 18 改善到 28~34、超 top-16 从 59 增到 67~75。⇒ 位置只占 15% 方差，去掉它换不来检索。
- **双边去 top-k 主成分**：in-sample `drop PC8` 极好（std 5.38→1.56、lift 6.48→4.74、合成针中位 **1**、超 top-16 **2/116**、SNR **3.04**），**但留一验证反向崩**——用后 70 页估 basis、在前 70 页评估时，真实针 lift 掉到 **0.48**、rank **10**。⇒ **140 页 × 16384 维估不出稳定的主成分**（高维小样本），in-sample 的漂亮数字是过拟合。
- **query 中心化**（`q_t − q̄_span`）：std 5.38→1.27 看着极好，但**真实针的 lift 同时从 +6.48 掉到 +0.68**（rank 5）、合成针中位 49。⇒ **背景与信号同向**，中心化把两者一起去掉。
- **白化 / 保留低方差方向**：`drop PC16` 起 SNR 跌破 1（0.91），`drop PC32` 只剩 0.60 lift。⇒ 没有"只放大信号"的方向。

**配套确认**：`cosine` 与 `dot` 同排名（061 结论复现）；**粒度 32 仍优于 64/128**；两轮采集的页均值 K 逐页 cos ≥ 0.9702（均值 0.9996）⇒ 采集可复现；`subblock_counts` 覆盖 6198/6230 子块。

**判定**：**成因查清、危害量化、但"去偏置"这条路线判 NO-GO**。①**成因**不是范数、不是 max 归约、不是 `k_norm` 权重、也不是"早期页更模板化"，而是 **query 的共同成分（模板/位置）与 k̄ 中随文档位置缓变的成分（PC2）对齐**；②**它只占 logit 方差的 15%，而 97% 的方差与 query 无关**——真正的量级是"页级背景"而不是"早期页"；③**任何线性变换都无法稳健分离背景与信号**（它们共享子空间）。⇒ **"早期页偏置"不是实现缺陷，是"1424-token 页粒度下检索信噪比"的体现（风险 R1 的定量形态）**。**不阻塞重物化**：真实针在引擎的 max 归约下 rank 1（lift +6.48）；**但"针落在文档后部"确实会被淹没（51% 的候选页）**，这是阶段 1 出口必须用**多深度 needle** 实测的项。

**caveat（勿当成通用常数）**：本步文档是**合成高重复文档**（3 个 4k 单元循环 49 次），其页级背景方差可能大于自然对话历史；"51% 被淹没"是这份文档上的量级。

**运维**：**收尾用 `tools/prod_watchdog.ps1` 恢复生产：boot0 一次即 FAST（8k 中位 123.34，三次 123.34/124.09/119.91，boot 94s），余量判据 34 MiB = OK** ⇒ 本步的源文件改动（`kvmem_workspace` 下 3 个文件）**没有**触发 AOT 重编译退化（生产路径不编译这些模块）。

**踩坑**：**用 baseline 的 lift 去评估修法会造出假改善**——"query 中心化"一度显示"合成针中位 rank 1、0/116 超 top-16"，换成该修法自身的真实 lift 后变成中位 49、77/116。**教训 = 修法评估必须用修法后的信号强度**。另：`sed -i` 会把仓库内 `.cmd` 的行尾从 CRLF 改成 LF（本轮踩到一次，已用 python 转回并用 Edit 工具改内容）。

## 步骤 061（2026-09-30）— KVMem K3 前半（raw-K 捕获 + Mean-K 索引 + 页级检索打分）：**机制 GO + 检索有信号（R1 部分消解）**

按《orcasaq2后续推进计划.md》§3 与设计档 §12.7 的 **K3 前三件**。**为什么先做"打分"而不是先做"重物化"**：风险 **R1**（论文 32-token 块 vs 我们 1424-token 页 ⇒ **检索可能根本无效**）若不先量，重物化（位置解耦 + 重 RoPE + 块表改写，本线最重工程）可能是白做。

**判定**：**机制 GO；R1 部分消解（检索有强信号，但粒度必须取 32 而非设计的 128；残余早期页偏置未解 → 062 结案）**。**未验证（勿当成已验）**：①**重物化完全未做** ⇒ 窗外 needle 仍答不出；②早期页偏置成因（062 已答）；③工作区/索引只增不减、无 LRU；④多轨迹并发（`--max-num-seqs 1`）；⑤性能（阶段 1 不判，且本臂无图模式）。

## 步骤 057（2026-09-29）— KVMem 阶段 1a **开工**：引擎侧「超池长 prompt 有界 prefill」机制打通

用户指令「开始推进」⇒ 按设计档 §6 开工第一件事 = **阶段 1a（冷启动 prefill 期 stage-out）**。本轮把"超池长 prompt 到底怎么 prefill 进来"从**做不到**变成**跑通**，并留下一条正控证明机制真的有界。

**问题定性（为什么必须动引擎）**：纯 vLLM 路径下请求自己的 KV 块在 prefill 期间不会被回收（长 prompt 必须整段驻留才能算后续 token 的注意力），池 3.4e9 只装 163,719 token ⇒ 262K prompt 永远申请不到块。**现状不是崩、是挂**：`scheduler_reserve_full_isl=True`（`config/scheduler.py:161`）让装不下的请求卡在等待队列不动——比崩更难发现（参考 #56 是同一条路径的 OOM 版）。

**选型 = 给 16 个 `full_attention` 层加逐层滑窗 `per_layer_sliding_window`（窗口 W）**：①单请求块需求从 `∝ prompt 长度` 变成 `∝ 窗口`（`SlidingWindowSpec.max_admission_blocks_per_request`）；②`SlidingWindowManager.remove_skipped_blocks` 每次 `allocate_slots` 前释放滑出窗口的块 ⇒ 驻留稳定 ~W；③注意力走 flashinfer 原生 **FA2 + `window_left`**（`use_fa2_nvfp4_kv` 在 SM120 为真）⇒ **nvfp4 可用**，且**不是**设计档 §5.1 否掉的那条 flex mask 路径（那条被 KV dtype 卡死）。

**⭐绕过的引擎一道门**：`CacheConfig.sliding_window` **只在 `layer_types` 全部是 `sliding_attention` 时才被填充**（`engine/arg_utils.py:2061-2067`，注释明写否则会覆盖交错模型里 global 层的窗口）⇒ 本模型 16 `full_attention` + 48 `linear_attention` 交错，**`--hf-overrides` 设 `sliding_window` 无效**；唯一入口是 `Attention(per_layer_sliding_window=...)`。

**实现**：`model_executor/models/qwen3_next.py` 新增 `_kvmem_per_layer_sliding_window(config, prefix)`——`VLLM_KVMEM_SW_WINDOW=N` 时**只对 `full_attention` 层**返回 N（草稿自带的 5 个 `sliding_attention` 层不受影响），**未设时返回 None、逐字节等价于改前**（实测生产 boot 布局数字与 055 基线逐项相同、日志无 step-057 行）。

**实测**：①**布局自动重算**——attn block **1456 → 1424**、mamba 页 padding 0.12% → 0.38%、`GPU KV cache size: 1,060,864 tokens / Maximum concurrency 4.05x @262,144`（生产 = `163,719 / 1.00x @163,072`）。②**冷超池 prompt 全跑通**：冷 **210K → TTFT 152.2 s**（≈1,360 tok/s）、冷 **256K → TTFT 185.2 s**（≈1,383 tok/s），均 needle 命中、无 OOM 无崩；**prefill 还比生产快**（~1,370 vs 867 tok/s），与参考 #34「prefill 单 token 成本 ∝ 视窗」同向。③**正控（本轮最关键）**：同 210K prompt，needle 埋 95% 深（窗内）**命中**、埋 10% 深（约 190K token 之前，窗外）**未命中**且模型自述"需要通读全文找这个 code"却找不到 ⇒ **滑窗真的在生效**；同时说明**滑窗给的是"近期性"不是"检索"**——正是 KVMem 检索层要补的那块。④**W=163,072 复验（阶段 1 主配置窗口，收尾补跑）**：`GPU KV cache size: 275,997 tokens / 1.05x @262,144` ⇒ **主配置窗口刚好装得下池（只剩 5% 余量）**；冷 **256K → TTFT 320.2 s**（≈800 tok/s，比 W=32,768 的 185 s 慢——窗口越宽注意力扫得越多）、needle 95% 深命中；冷 **210K → 249.1 s**、needle 10% 深未命中（~20.7K 位置落在窗口 `[44K, 207K]` 之外，与边界自洽）⇒ **窗口大小是"检索质量 / prefill 速度 / 池余量"的三向旋钮**。⑤余量判据 OK（共享 − 8,298 = 0 MiB）；臂上多出的 ~1 GiB 独显余量主要来自**去掉投机草稿**，不是滑窗省的。

**检索参数**：索引 128-token 子块、页分归约取**页内子块 max**、打分用 **softmax-over-pages**（非原始点积，参考明确说原始 `q·k̄` 偏向高范数 sink/早期块）、**只对当前 query span 打分**、sink/recent mask 成 -inf、选满后**按时间序**分配槽位、**打分必须在 GPU 上分块做**（参考用 CPU mean-K，32k 时要 4.7 秒，他们自己标为最大剩余账单）。

**捕获钩子**：**q 与 k 都在 RoPE 前捕获**（索引与 query 同在"内容帧" ⇒ 打分不需要任何逆旋转）；**我们的两个坑**——①参考的 `ggml_rope_ext` 非 in-place 所以能 `set_output()` 白拿副本，**我们的 `ops.rotary_embedding` 是 in-place 的**（`rotary_embedding/base.py:242-252`）⇒ **必须显式 clone**；②生产走融合 kernel `fused_qk_rmsnorm_rope_gate`（`qwen3_next.py:403`）抓不到中间量 ⇒ **阶段 1 强制走 eager 路径**（`qwen3_next.py:424-444`）、只对 16 层 full attention 留档、**只对"新 prefill 的差量 token"捕获**（整视窗会是 5.4 GiB）、代价认下来（eager 与融合 kernel 不逐位一致 ⇒ **臂内自洽、不跨臂比 PPL**；性能不计入阶段 1 判据）、阶段 2 换融合 kernel 变体。

**存储形态**：溢写 = V（nvfp4 原样）+ K 的非旋转 192 维（nvfp4 原样，位置无关）+ K 的旋转 64 维（**fp16 raw，重建权威**）；重物化 = 只对那 64 维按槽位位置单次重烘焙 + 重新量化，其余原样拷贝。

**session 协议**：**内容哈希轨迹键（root task message + current query）+ LCP 差量，客户端零改动**；prompt 缩水 > max(1024,1%) ⇒ 冷启动；**明确边界 = 客户端侧压缩时我们只能冷启动**（能力来自"服务端接受更长 transcript"）。
