## 步骤 057（2026-09-29）— KVMem 阶段 1a **开工**：引擎侧「超池长 prompt 有界 prefill」机制打通

用户指令「开始推进」⇒ 按设计档 §6 开工第一件事 = **阶段 1a（冷启动 prefill 期 stage-out）**。本轮把"超池长 prompt 到底怎么 prefill 进来"从**做不到**变成**跑通**，并留下一条正控证明机制真的有界。

**问题定性（为什么必须动引擎）**：纯 vLLM 路径下请求自己的 KV 块在 prefill 期间不会被回收（长 prompt 必须整段驻留才能算后续 token 的注意力），池 3.4e9 只装 163,719 token ⇒ 262K prompt 永远申请不到块。**现状不是崩、是挂**：`scheduler_reserve_full_isl=True`（`config/scheduler.py:161`）让装不下的请求卡在等待队列不动——比崩更难发现（参考 #56 是同一条路径的 OOM 版）。

**选型 = 给 16 个 `full_attention` 层加逐层滑窗 `per_layer_sliding_window`（窗口 W）**：①单请求块需求从 `∝ prompt 长度` 变成 `∝ 窗口`（`SlidingWindowSpec.max_admission_blocks_per_request`）；②`SlidingWindowManager.remove_skipped_blocks` 每次 `allocate_slots` 前释放滑出窗口的块 ⇒ 驻留稳定 ~W；③注意力走 flashinfer 原生 **FA2 + `window_left`**（`use_fa2_nvfp4_kv` 在 SM120 为真）⇒ **nvfp4 可用**，且**不是**设计档 §5.1 否掉的那条 flex mask 路径（那条被 KV dtype 卡死）。

**⭐绕过的引擎一道门**：`CacheConfig.sliding_window` **只在 `layer_types` 全部是 `sliding_attention` 时才被填充**（`engine/arg_utils.py:2061-2067`，注释明写否则会覆盖交错模型里 global 层的窗口）⇒ 本模型 16 `full_attention` + 48 `linear_attention` 交错，**`--hf-overrides` 设 `sliding_window` 无效**；唯一入口是 `Attention(per_layer_sliding_window=...)`。

**实现**：`model_executor/models/qwen3_next.py` 新增 `_kvmem_per_layer_sliding_window(config, prefix)`——`VLLM_KVMEM_SW_WINDOW=N` 时**只对 `full_attention` 层**返回 N（草稿自带的 5 个 `sliding_attention` 层不受影响），**未设时返回 None、逐字节等价于改前**（实测生产 boot 布局数字与 055 基线逐项相同、日志无 step-057 行）。

**实测**：①**布局自动重算**——attn block **1456 → 1424**、mamba 页 padding 0.12% → 0.38%、`GPU KV cache size: 1,060,864 tokens / Maximum concurrency 4.05x @262,144`（生产 = `163,719 / 1.00x @163,072`）。②**冷超池 prompt 全跑通**：冷 **210K → TTFT 152.2 s**（≈1,360 tok/s）、冷 **256K → TTFT 185.2 s**（≈1,383 tok/s），均 needle 命中、无 OOM 无崩；**prefill 还比生产快**（~1,370 vs 867 tok/s），与参考 #34「prefill 单 token 成本 ∝ 视窗」同向。③**正控（本轮最关键）**：同 210K prompt，needle 埋 95% 深（窗内）**命中**、埋 10% 深（约 190K token 之前，窗外）**未命中**且模型自述"需要通读全文找这个 code"却找不到 ⇒ **滑窗真的在生效**；同时说明**滑窗给的是"近期性"不是"检索"**——正是 KVMem 检索层要补的那块。④**W=163,072 复验（阶段 1 主配置窗口，收尾补跑）**：`GPU KV cache size: 275,997 tokens / 1.05x @262,144` ⇒ **主配置窗口刚好装得下池（只剩 5% 余量）**；冷 **256K → TTFT 320.2 s**（≈800 tok/s，比 W=32,768 的 185 s 慢——窗口越宽注意力扫得越多）、needle 95% 深命中；冷 **210K → 249.1 s**、needle 10% 深未命中（~20.7K 位置落在窗口 `[44K, 207K]` 之外，与边界自洽）⇒ **窗口大小是"检索质量 / prefill 速度 / 池余量"的三向旋钮**。⑤余量判据 OK（共享 − 8,298 = 0 MiB）；臂上多出的 ~1 GiB 独显余量主要来自**去掉投机草稿**，不是滑窗省的。

**⭐必须记清的边界（"溢写"只做到一半）**：滑出窗口的历史 KV 是**被丢掉**而不是被保存；offload 层确实写盘（`kv_offload_store_bytes = 314,671,104`，200K 请求期间）但**只有 ~300 MB**——它只存"滑窗可达的那几块"（当 prefix cache 用）。⇒ 阶段 1a 的"不崩不 OOM"半边达成，**"溢写"半边仍需 KVMem 自己的工作区 store**：copy-before-free 钩子落在 `SingleTypeKVCacheManager._remove_blocks_in_range`（`block_pool.free_blocks(freed)` 之前），键从 block hash 改成 `(轨迹, 页序号)`，可复用 `v1/kv_offload/` 的 CPU 层与 `OffloadingConnector` 的 pending-job 记账。

**⭐踩到的坑（重要运维结论）**：改 `qwen3_next.py` 会**改掉 AOT 编译缓存的键**（源码参与 hash）⇒ **部署本补丁后生产第一次 boot 必然重编译**，而冷重编译 boot 处在退化态：同配置首 boot 实测 8k 101-104、**146k 只有 34.12 tok/s**（余量判据显示被挤 68 MiB）；**第二 boot（缓存命中，warmup 46.6 s → 3.05 s）立刻恢复 146k 104-108、8k 117-124.5、needle 6/6**。⇒ **本补丁上线必须双 boot（或走 `tools/prod_watchdog.ps1`）**；也再次说明"拿单次 boot 判性能回归"会误判（本轮差点把 34.12 当成补丁引入的回归）。另：`anchor_longctx.py` 会先跑同 prompt 的 warmup，**首个 TTFT 是前缀缓存命中、会把真实 prefill 藏掉**（本轮第一版就踩了，198K prompt 报 0.52 s）⇒ 冷 prefill 必须用新探针 `_tmp_line_b/kvmem_cold_prefill.py`（haystack 嵌随机 nonce）。

**交付**：①`VLLM_KVMEM_SW_WINDOW` 门控补丁（`qwen3_next.py`）②新工具 `tools/sync_venv.py`（仓库↔venv 同步/校验，**保留目标侧行尾**——本仓 `vllm/` LF、venv 安装副本 CRLF，纯字节比较会全树误报；实测 2724 个 `.py` 里 1893 CRLF / 831 LF，改前内容全等）③实验臂 `_tmp_line_b/serve_kvmem_sw32k.cmd` + `serve_kvmem_sw163k.cmd`（用户指令：无投机 ⇒ `--cudagraph-capture-sizes 1`，实测 8k 61.2 → 69.4 tok/s，**+13%**）④探针 `_tmp_line_b/kvmem_cold_prefill.py` ⑤设计档新增 §12。**生产配置未变**（046：池值 3.4e9 / L=163,072 / 容量 163,719；补丁默认关闭），末轮恢复现役。

**下一步（阶段 1a 剩余）**：①**1a-2 copy-before-free 钩子**（"溢写"的另一半）；②准入守卫复核（工作区上限 262,144 与"视窗"两个上限都要干净 400 而不是卡队列）；③阶段 1 主体（raw K 捕获 → 检索 → 重物化 → identity canary / 紧预算 needle 对照），仍未开工。**未验证（勿当成已验）**：滑窗对 8k/146k 稳态解码的性能影响（本臂无投机，数字不可与生产比）；W=163,072 的冷 256K 预填时间；重物化/检索。

**⭐设计定稿全文 = `docs/vllm-030win-调研-KVMem虚拟化KV工作区.md`（唯一设计权威，接手先读它）**。

**目标能力** = (A 主) 接受超长 transcript（工作区上限 **262,144**，客户端照旧发全量、服务端把超视窗历史虚拟化到 host）；(B 副产品) 免客户端压缩、免全量重 prefill；(C 结构收益) 上下文长度与 GPU 池**解耦**（缩池可换显存余量 ⇒ 直接对冲 049 悬崖）。**明确非目标 = 长上下文召回**（作者本人回复"长上下文召回不是这个框架最擅长的，建议 `-c` ≤ 200k"，其定位是 agent 长程任务）。

**⭐核心架构决策 = (C) 固定槽位布局**：布局 `[sink S | 检索槽 N | recent R | query q | 生成预留 g]`，**槽位位置在请求开始前由确定性规则算出**；关键不变式 = **query 位置 `B=S+N+R` 与"最终选了哪些块"无关**（N 固定，选择只决定槽内容）⇒ 一次消掉三个问题：①**不需要重 prefill** ⇒ GDN 每步只前进一次 ⇒ **不需要 GDN 状态快照/恢复**（绕开 `num_prefill_checkpoint_blocks=0` 的硬约束）②**视窗稠密连续** ⇒ **不需要 mask** ⇒ 生产注意力路径（nvfp4 flashinfer + FULL_AND_PIECEWISE）一行不动 ③**不存在 "query replay" 概念** ⇒ 参考实现 #43/#13 的"跳过 replay → 全量重 prefill 136 秒"退化路径**结构性不存在**。

**为什么不用参考的路线**：它走"原始位置 + 洞 + KQ mask"（v0.3.0 里程碑明写"**禁止 pack `[0..W)`**"、架构文档写"**no unrotated raw-K and no re-RoPE on the product path**"），但 **vLLM 的 mask 路径只支持 fp16/bf16 KV**（`FlexAttentionBackend.supported_kv_cache_dtypes = ["auto","float16","bfloat16"]`）而生产 KV 是 nvfp4 ⇒ 改 flex 要么视窗缩到 ~48K（远小于生产 163K，对 ≤163K 的 prompt 反而退化）、要么给 nvfp4 新写 mask/稀疏 kernel（动全栈最脆弱处）；**论文/QW3 的"重 prefill query"路线也被否**（要 GDN 快照 + 带 #43 同族退化路径）。

**⭐我们的三条硬约束**（决定一切）：①**块粒度 = 1456 token**（混合模型页对齐强制：mamba page 1,675,264 B ≈ attn page 1456×1152 = 1,677,312 B；**改小到 128 会让容量掉约 11×**）⇒ 检索**索引**用 128-token 子块、**搬运**按整页；②**GDN 循环状态不能回退**（见上）；③**显存余量悬崖**（049/055：池后任何新分配 64 MiB 即 8k 解码 121→85 且不回弹；参考自己的 capture staging 默认是 **448 MB pinned + 448 MB 显存**）⇒ **所有新增显存必须在池创建之前分配、并从池预算里扣出来，预算 192 MiB**（索引 staging 2×64 + 一页重物化暂存 2×25.6）。

**host 预算**（用户 09-29 裁定：**offload 可缩到 2G/1G，不用管 NVMe**）：工作区 262,144 的全量 KV = 4.83 GiB（nvfp4 18,432 B/token），实际 host 需求约 **3.7 GiB**（溢写 V + 位置无关 192 维 K ≈ 1.5 GiB + raw K 权威 fp16 只存旋转 64 维 = 2.1 GiB + 索引 67 MiB）——落在"offload 缩到 1-2 GiB 后可用"范围内，**不需要 NVMe**（对照：参考同规模 RSS 峰值 13.5 GiB，因为它用 Q8_0 32 KiB/token）。

**⭐参考实现的已暴露缺陷取证（open 未修，逐条对应我们的设计决策，详见调研档 §4）**：

- **#13 closed（rc3 修，作者 09-28 回 "repaired by rc3"）→ #43 open（同根因的优雅降级版，0 评论未修）** = `query_replay_fits()` 把强制 replay 范围（sink+后缀）与**策略预算**（288 块）比而非**物理池**（416 槽）⇒ `required 293 > 288` ⇒ replay 跳过 + `mandatory_trim` 恰好丢掉**紧贴 query 之前刚读到的工具输出**（5 块）+ **83,909 token 全量重 prefill `first_ms=136,013`**；
- **#4 open** = **>210K 中段串台**（问敦煌答滇池的编号，有报告者测 100% 可复现、坍缩目标固定），报告者埋 fprintf 确认**检索与选块都正常**、"模型从窗口里读出来的内容就是错的/糊的"，归因**量化副本上反复 in-place delta re-RoPE 累积误差**（机制标注未确认）；作者建议 `-c` ≤ 200k；另一发现**提问顺序是隐藏变量**（同文档 3% 起问 4/6、50% 起问 6/6）⇒ **跨顺序不可比**；
- **#56 open** = **全量重发会杀服**（池 81,920、prompt 81,056+gen → CUDA OOM → ggml_abort → 整进程死 + 崩溃循环；守卫只查 `n_ctx` 从不查池；原文点名这就是 "agentic loop with **full-history resend**"——**正是我们的客户端模式**）；
- **#55 open** = capture staging 按进程历史峰值定尺最大 448 MB pinned + 448 MB 显存且永不自适应；
- **#34 open** = prefill 单 token 成本 ∝ 视窗（53,248→2.98 µs/token、28,672→1.49）**但缩小视窗不伤检索质量**（needle 埋在工作集外 93K 仍召回）⇒ 缩池是双赢；
- **#22/#82** = Windows 多轮 agent 解码被钉 12-20 tok/s（**参考性能不可作我们的锚**，我们生产 8k 122.58/146k 107.73）；
- **#11/#23/#73** = Windows 自建脆弱（MSVC 自建首请求 `0xC0000409`、24K+ prompt 崩、长上下文"prefill failed or cancelled 然后卡循环预填充"）。

**我们的规避映射**：不做 delta re-RoPE（**每次入槽一律从 raw K 单次重建 ⇒ 零漂移** ⇒ #4 机制不存在，**"8 次 remap/累计位移阈值"那套参数作废**）；(C) 布局无 replay ⇒ 免疫 #43；**冷启动 prefill 期 stage-out 列为阶段 1 独立子里程碑 1a**（#56 是我们的必经路径）；192 MiB 池前分配（免疫 #55）。

**⭐参数标定**：阶段 1 主配置 = 视窗 **163,072** / 生成预留 **32,768** / sink **1,456（1 页）** / recent **动态 = 最近一次工具输出长度 clamp [16K, 64K]** / 检索余量约 65-113K（留取率 62%，**弱信号**）；**96K 压力配置** = 视窗 98,304 / 生成 32,768 / sink 1,456 / recent 32,768 / 检索 ~31K（**留取率 21%，检索变刚需**）；identity 态 = workspace ≤ budget_max 时整段全驻留；**工作区能力上限 262,144，200K-262K 标"已知风险带"只记录不判死、阶段 1 闸门 ≤200K**；**budget 下界 = sink + recent + ≥16K 检索（约 96K）**——`recent` 按"最大工具输出"定尺是**直接来自 #13/#43 的教训**（紧贴 query 的工具输出后缀 37,288 token 超过 budget 36,864 ⇒ replay 被跳过 + 刚读的工具输出被 trim）。

**检索参数**：索引 128-token 子块、页分归约取**页内子块 max**、打分用 **softmax-over-pages**（非原始点积，参考明确说原始 `q·k̄` 偏向高范数 sink/早期块）、**只对当前 query span 打分**、sink/recent mask 成 -inf、选满后**按时间序**分配槽位、**打分必须在 GPU 上分块做**（参考用 CPU mean-K，32k 时要 4.7 秒，他们自己标为最大剩余账单）。

**捕获钩子**：**q 与 k 都在 RoPE 前捕获**（索引与 query 同在"内容帧" ⇒ 打分不需要任何逆旋转）；**我们的两个坑**——①参考的 `ggml_rope_ext` 非 in-place 所以能 `set_output()` 白拿副本，**我们的 `ops.rotary_embedding` 是 in-place 的**（`rotary_embedding/base.py:242-252`）⇒ **必须显式 clone**；②生产走融合 kernel `fused_qk_rmsnorm_rope_gate`（`qwen3_next.py:403`）抓不到中间量 ⇒ **阶段 1 强制走 eager 路径**（`qwen3_next.py:424-444`）、只对 16 层 full attention 留档、**只对"新 prefill 的差量 token"捕获**（整视窗会是 5.4 GiB）、代价认下来（eager 与融合 kernel 不逐位一致 ⇒ **臂内自洽、不跨臂比 PPL**；性能不计入阶段 1 判据）、阶段 2 换融合 kernel 变体。

**存储形态**：溢写 = V（nvfp4 原样）+ K 的非旋转 192 维（nvfp4 原样，位置无关）+ K 的旋转 64 维（**fp16 raw，重建权威**）；重物化 = 只对那 64 维按槽位位置单次重烘焙 + 重新量化，其余原样拷贝。

**session 协议**：**内容哈希轨迹键（root task message + current query）+ LCP 差量，客户端零改动**；prompt 缩水 > max(1024,1%) ⇒ 冷启动；**明确边界 = 客户端侧压缩时我们只能冷启动**（能力来自"服务端接受更长 transcript"）。

**接口落点**：`KVConnectorBase_V1` 子类为主（跨请求 store + 调度/worker 两侧 + 已有 Windows CPU 层）+ `AttentionMetadataBuilder.update_block_table`（`v1/attention/backend.py:675`，`supports_update_block_table` 门控）补一刀做视窗装配；存储复用 `v1/kv_offload/` CPU 层但**键从 block hash 改成 (轨迹, 页序号)**。
