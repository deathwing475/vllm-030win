## 2026-09-28（二十六）— 慢态识别+规避交付：显存指纹破维、性能连续谱定性、watchdog 实战验证（步骤 042）

接 040/041 头名「慢态的根因与规避」。15 boot 实测（census 8 + watchdog 3 + tick 4），三个认知修正 + 一个交付：

- **显存指纹破维（040 的「专用显存低 284 MiB」指纹被推翻）**：census1 普查（8 boot，health 后抓卡级 used + pin 日志 + 8k 探针×3）里，慢 boot 15,474 MiB（中位 83.99 tok/s）与快 boot 15,486 MiB（中位 117-122）**只差 12 MiB**；且快慢差跨天漂移（040：15,538/15,254；今天：15,486/15,280-15,474）。专用显存只是影子变量 —— 029/030 的强相关性属于已被 pin_shim 钉死的草稿放置机制。
- **性能是连续谱非二态**：15 boot 的 8k 单条全域 **83.45-129.27 tok/s**（低带 83-99 / 中带 101-110 / 高带 112-129）；watchdog 三连 boot 依次 89.15 → 103.59 → 109.86 是最直观的展示。040/041 的「快/慢二态」是小样本印象。
- **引擎侧零可见**：pin 日志 8 boot（含 2 慢）逐字节相同（与 040 的 15-boot 结论一致）；引擎阶段日志快慢逐行等价（init engine 22.33 vs 22.43s）；**「Initial free memory 14.68 GiB」快慢逐位相同无归因价值** —— tick 1Hz 曲线证明它是 boot 起点快照（t=1-9 的 free 15,037 MiB），不反映 KV 前状态。分叉在 WDDM 物理放置层，与草稿放置是**两个独立随机源**。
- **tick 1Hz 曲线（4 boot 全 fast，slow 对照未抽到）**：EngineCore 全程曲线分段清晰：载入 15,037→3,364 → 稳态 3,701 → **t=23-27 free=0 压力窗（草稿 repack）** → PIN 后 3,223 → AOT/KV 段 3,357→3,047 → t=42 起满载 0（常态）。工具已固化（`_tmp_line_b/dbg_shim` + `tick_arm.py`），抽到 slow 对照即可收口分叉定位。
- **✅ 交付：`tools/prod_watchdog.ps1`**（kill→boot→health→8k needle 探针×3 中位 ≥105 判快→慢则杀重启上限 3 次；退出码 0/2/3/4）。实战：3 boot 2 重启后留下 median 109.86、needle 3/3 的服务（exit 0），**实测把 89 级 boot 换成 110 级（+24%）**——20% 级方差从「随机命中」变为「启动时消除」。median ≥105 ⇒ 90% 档 ~≥93，用户判据①（≥85）有余量。

**踩坑**：①`make_launcher` 用 `open()` 默认 universal-newlines 读 CRLF 的 .cmd 再写回 → 全文件变 LF、cmd 吃 rem/set 行首、launcher 散架（**CRLF 坑第三次踩**；修复 = 读写都 `newline=""` + 断言 `\r\n`）；②WDDM 下 nvidia-smi 无 Dedicated/Shared 分列、per-process 显存报 `[N/A]` —— 卡级 `memory.used` 是唯一可靠外置口径。

**下一步**：草稿权重再压缩（现头名，AutoRound 独立立项）或 tick 快慢对照收口；生产启动建议走 watchdog（配置变更后须重标定阈值 105）。

## 2026-09-28（二十二）— 阶段 3 续：D 组（SM120 专项）与 C6 全量评估，全部 NO-GO（步骤 038）

**做了什么**：接用户「按你的来，调顺序」——把原定序里排最后的 **D 组**（SM120/Blackwell 消费卡专项）与 **C6**（量化新能力包）提前评估，因为从功能菜单看这两批理论上最贴近本栈。①确认硬件（`nvidia-smi` ⇒ RTX 5070 Ti / compute_cap 12.0 = **SM120** / 16,303 MiB）；②拉 D 组与 C6 的 PR diff 并跑覆盖率自检；③**把 D4 的 `#55715` 逐 hunk 移植进底座仓并实测**；④源码核对 D6/C6 的平台与 dtype 前提。

**判定**：**D 组与 C6 全部 NO-GO**。

**D4（GDN prefill SM12x）—— 移植成功但 Windows 上不可用，已回退**：`#55715` 给 `_resolve_gdn_prefill_backend` 加一个 SM12.x 分支（SM12.x + `head_k_dim == 128` + `cuda_runtime >= 13` ⇒ 支持 flashinfer）。**移植精度自检 9/9 = 100%**、锚点逐字一致、依赖方法（`is_device_capability_family` / `get_cuda_runtime_major`）在 0.29 都在；移植后启动**确实切换了后端路径**，但**引擎启动失败**：`ModuleNotFoundError: No module named 'cutlass'`（48 个 GDN 层 warmup 全失败 + EngineCore failed to start）。**根因定罪**：flashinfer 0.6.18 的 SM120 GDN prefill 是 **CuTe DSL 实现**（`gdn_prefill.py` 里 `# SM120 Blackwell path (CuTe DSL kernel)` → `chunk_gated_delta_rule_sm120`，`gdn_kernels/` 里 import `cutlass.cute`），而 **`nvidia-cutlass-dsl` 的包元数据明写 `Classifier: Operating System :: POSIX :: Linux`** ⇒ **CuTe DSL 不支持 Windows**（上游 `_resolve_gdn_prefill_backend` 原本不含 SM12.x，正是因为该判定假设 Linux）。**已 `git checkout` 回退**，venv 恢复逐字节一致，重启验证 `Using Triton/FLA GDN prefill kernel` 恢复、容量不变、三段捕获全过、health 200。

**D 组其余项**：**D1**（B12X_ATTN）历史已 NO-GO（extend 慢 18%）；**D2**（W4A4 NVFP4 在 SM120 成为默认）—— 本栈权重是 **WNA16 int3**，不是 nvfp4，路径不经过；**D3**（DeepGEMM 钉 vllm fork 2.8.0）—— 改的是 `cmake/external_projects/deepgemm.cmake` + Dockerfile + install 脚本（**构建期**），本栈是**预编译 win whl**、无 CMake 流程，且 DeepGEMM 主要服务 MoE（本模型是 dense 27B）；**D4 另一半**（`#53835`）—— 只给 `FUSED_GDN_DECODE_ARCHS` 加 `11.0f`（SM110），本机 SM120（`12.0f` 早已在列）；**D5**（SM12x blockwise FP8 swizzle）—— 本栈不用 FP8；**D6**（`#55031` NVFP4 KV FMHA + `#51925` fused add-RMSNorm+NVFP4）—— `#55031` 第一处是给 `fused_output_quant_supported` 加「nvfp4 KV + nvfp4 输出不融合」的保护，但 0.29 的该函数**已含 `is_device_capability_family(100)` 条件**（**本机 SM120 不满足 ⇒ 融合本就没启用，无需保护**），第二处只是去掉几处多余的 dtype cast；`#51925` 是**纯 NVFP4** 的 add+RMSNorm+fp4 量化融合（`add_rmsnorm_fp4quant`）⇒ 本栈 int3 不适用。

**C6 全 NO-GO**：该包绝大多数是 **NVFP4/CuTeDSL 专用**（FlashInfer CuTeDSL NVFP4 W4A16 默认替代 Marlin、NVFP4 torch linear backend、`nvfp4_fp8_ds_mla` KV cache）⇒ 本栈 int3 权重不经过、且 CuTe DSL 在 Windows 不可用；**唯一理论相关的 AutoRound 2/3/5/6/7-bit 是离线量化算法**（需要 AutoRound 库 + 校准数据重跑量化流程），**不是 vLLM 推理代码的可移植改动**，应作为独立量化实验立项。

**阶段 3 剩余项的适用性判定**（基于技术栈）：**C1**（Fast Start `ipc_cache`）—— 收益是**重启提速**（本栈启动 39s 中权重加载占 15.25s），但面向 nvfp4 checkpoint 与多节点 TP，且本栈已有 AOT 编译缓存；**A8**（API/结构化输出修复）—— 纯 API 层，对推理性能/上下文无影响；**A9**（安全修复）—— 仅公网服务需要，本栈是本地部署；**A2**（RL/训练侧）—— 本栈不做 RL；**B7**（Qwen3.5 系配套：DSpark padded-vocab 草稿、多模态 MTP）—— 本栈草稿是 **DFlash2**（非 DSpark）、不使用多模态 MTP；**C8**（KV offload 新能力）—— PR 集中在 `vllm/v1/kv_offload/tiering/`（KVCR 二级 tier）与 `tiering/p2p/`（多机 P2P），本栈单卡用的是 **prefix-cache 后端的 `--kv-offloading-size`**，不经过 tiering 子系统。

**根因一句话**：**D 组/C6 的设计前提是 nvfp4/FP8 权重 + CuTe DSL + Linux，而本栈是 compressed_tensors WNA16 int3 + Windows + 预编译 whl。** 唯一直接命中本栈 GDN 的 D4 被 CuTe DSL 的 Linux-only 属性挡住（**实测定罪，非推断**）。

**教训**：**「平台专项」类移植必须先把「依赖在目标 OS 上是否存在」查清楚** —— 本次 `#55715` 的代码移植精度 100%、锚点逐字一致、依赖方法齐备，**但运行时依赖 `nvidia-cutlass-dsl` 是 Linux-only** ⇒ 白做一轮启动验收。**今后凡涉及 CuTe DSL / DeepGEMM / CUTLASS 的移植项，先查包元数据的 `Classifier: Operating System`。**
