## 2026-09-29（四十一）— 步骤 057：KVMem 阶段 1a **开工** —— 引擎侧「超池长 prompt 有界 prefill」机制打通（`VLLM_KVMEM_SW_WINDOW` 门控逐层滑窗；冷 256K prompt 185 s 跑完不 OOM；**窗外 needle 必失**作正控）

用户指令「开始推进」⇒ 按设计档 §6 开工第一件事 = **阶段 1a（冷启动 prefill 期 stage-out）**。本轮把"超池长 prompt 到底怎么 prefill 进来"从**做不到**变成**跑通**，并留下一条正控证明机制真的有界。

- **问题定性（为什么必须动引擎）**：纯 vLLM 路径下请求自己的 KV 块在 prefill 期间不会被回收（长 prompt 必须整段驻留才能算后续 token 的注意力），池 3.4e9 只装 163,719 token ⇒ 262K prompt 永远申请不到块。**现状不是崩、是挂**：`scheduler_reserve_full_isl=True`（`config/scheduler.py:161`）让装不下的请求卡在等待队列不动——比崩更难发现。参考 #56 的"全量重发杀服"正是同一条路径（它那边 OOM 崩，我们这边静默挂）。
- **选型：给 16 个 `full_attention` 层加逐层滑窗 `per_layer_sliding_window`（窗口 W）**。三条收益：①**单请求块需求从 `∝ prompt 长度` 变成 `∝ 窗口`**（`SlidingWindowSpec.max_admission_blocks_per_request`）；②`SlidingWindowManager.remove_skipped_blocks` 每次 `allocate_slots` 前释放滑出窗口的块 ⇒ 驻留稳定 ~W；③注意力走 flashinfer 原生 **FA2 + `window_left`**（`use_fa2_nvfp4_kv` 在 SM120 为真）⇒ **nvfp4 可用**，且**不是**设计档 §5.1 否掉的那条 flex mask 路径（那条被 KV dtype 卡死）。
- **⭐绕过的引擎一道门**：`CacheConfig.sliding_window` **只在 `layer_types` 全部是 `sliding_attention` 时才被填充**（`engine/arg_utils.py:2061-2067`，注释明写否则会覆盖交错模型里 global 层的窗口）⇒ 本模型 16 `full_attention` + 48 `linear_attention` 交错，**`--hf-overrides` 设 `sliding_window` 无效**；唯一入口是 `Attention(per_layer_sliding_window=...)`。故在 `model_executor/models/qwen3_next.py` 新增 `_kvmem_per_layer_sliding_window()`：`VLLM_KVMEM_SW_WINDOW=N` 时只对 `full_attention` 层返回 N（草稿自带的 5 个 `sliding_attention` 层不受影响），**未设时返回 None、逐字节等价于改前**（实测生产 boot 布局数字与 055 基线逐项相同、日志无 step-057 行）。
- **结果**：①**布局自动重算**——attn block **1456 → 1424**、mamba 页 padding 0.12% → 0.38%、`GPU KV cache size: 1,060,864 tokens / Maximum concurrency 4.05x @262,144`（生产 = `163,719 / 1.00x @163,072`）。②**冷超池 prompt 全跑通**：冷 **210K → TTFT 152.2 s**（≈1,360 tok/s）、冷 **256K → TTFT 185.2 s**（≈1,383 tok/s），均 needle 命中、无 OOM 无崩；**prefill 还比生产快**（~1,370 vs 867 tok/s），与参考 #34「prefill 单 token 成本 ∝ 视窗」同向。③**正控（本轮最关键）**：同 210K prompt，needle 埋 95% 深（窗内）**命中**、埋 10% 深（约 190K token 之前，窗外）**未命中**且模型自述"需要通读全文找这个 code"却找不到 ⇒ **滑窗真的在生效，不是"其实做了全注意力"**；同时说明**滑窗给的是"近期性"不是"检索"**——正是 KVMem 检索层要补的那块。④**W=163,072 复验（阶段 1 主配置窗口，收尾补跑）**：臂 boot 报 `GPU KV cache size: 275,997 tokens / 1.05x @262,144` ⇒ **主配置窗口刚好装得下池**（只剩 5% 余量，是后续要盯的紧处）；冷 **256K → TTFT 320.2 s**（≈800 tok/s；比 W=32,768 的 185 s 慢——**窗口越宽注意力扫得越多**，与 #34 同向）、needle 95% 深命中；冷 **210K → 249.1 s**、needle 10% 深**未命中**（该位置 ~20.7K 落在窗口 `[44K, 207K]` 之外，与窗口边界自洽）⇒ **窗口大小是"检索质量 / prefill 速度 / 池余量"的三向旋钮，阶段 2 标定要当一等参数**。⑤余量判据 OK（共享 − 8,298 = 0 MiB）；注意臂上多出的 ~1 GiB 独显余量主要来自**去掉投机草稿**，不是滑窗省的。
- **⭐必须记清的边界（"溢写"只做到一半）**：滑出窗口的历史 KV 是**被丢掉**而不是被保存；offload 层确实写盘（`kv_offload_store_bytes = 314,671,104`，200K 请求期间）但**只有 ~300 MB**——它只存"滑窗可达的那几块"（当 prefix cache 用）。⇒ 阶段 1a 的"不崩不 OOM"半边达成，**"溢写"半边仍需 KVMem 自己的工作区 store**：copy-before-free 钩子落在 `SingleTypeKVCacheManager._remove_blocks_in_range`（`block_pool.free_blocks(freed)` 之前），键从 block hash 改成 `(轨迹, 页序号)`，可复用 `v1/kv_offload/` 的 CPU 层与 `OffloadingConnector` 的 pending-job 记账。
- **⭐踩到的坑（重要运维结论）**：改 `qwen3_next.py` 会**改掉 AOT 编译缓存的键**（源码参与 hash）⇒ **部署本补丁后生产第一次 boot 必然重编译**，而冷重编译 boot 处在退化态：同配置首 boot 实测 8k 101-104、**146k 只有 34.12 tok/s**（余量判据显示被挤 68 MiB）；**第二 boot（缓存命中，warmup 46.6 s → 3.05 s）立刻恢复 146k 104-108、8k 117-124.5、needle 6/6**。⇒ **本补丁上线必须双 boot（或走 `tools/prod_watchdog.ps1`）**；也再次说明"拿单次 boot 判性能回归"会误判（本轮差点把 34.12 当成补丁引入的回归）。
- **⭐新观察（余量悬崖第四个触发面：杀服后立刻重启）**：恢复现役时**连续 4 次"kill 后 5 s 就 boot"全部被挤**（38/68/64/322 MiB，8k 落 100-104 带）；改成「**kill → 轮询 `nvidia-smi` 直到独显 used 落回 ~124 MiB → 再 boot**」后**一次就干净**（被挤 **0**、dedicated **15,497.8** / shared **8,298** 与 049 快档基线逐字节相同、8k **120.16/121.25/120.24**、needle 3/3）。与 049「**boot 中途压力**比 boot 前常驻贵得多（56 vs 111）」同族：上一个引擎的 VRAM 还没被 WDDM 真正归还时启动新引擎 = 在新 boot 的中途制造压力。**建议进 watchdog**：杀服后先轮询落回 <800 MiB 再起（n=1，但 4:1 对比足够支撑这条廉价习惯）。这 4 次被挤全在**补丁关闭**的现役配置上 ⇒ 与滑窗补丁无关。
- **交付**：①`VLLM_KVMEM_SW_WINDOW` 门控补丁（`qwen3_next.py`）②新工具 `tools/sync_venv.py`（仓库↔venv 同步/校验，**保留目标侧行尾**——本仓 `vllm/` LF、venv 安装副本 CRLF，纯字节比较会全树误报；实测 2724 个 `.py` 里 1893 CRLF / 831 LF，改前内容全等）③实验臂 `_tmp_line_b/serve_kvmem_sw32k.cmd` + `serve_kvmem_sw163k.cmd`（用户指令：无投机 ⇒ `--cudagraph-capture-sizes 1`，实测 8k 61.2 → 69.4 tok/s，**+13%**）④探针 `_tmp_line_b/kvmem_cold_prefill.py`（**`anchor_longctx.py` 会先 warmup 同 prompt，首个 TTFT 是前缀缓存命中、会把真实 prefill 藏掉**——本轮第一版就踩了，198K prompt 报 0.52 s）⑤设计档新增 §12。**生产配置未变**（046：池值 3.4e9 / L=163,072 / 容量 163,719；补丁默认关闭），末轮恢复现役。

## 2026-09-28（二十七）— 草稿权重再压缩收档：clip-H GPTQ 臂 gptq4c NO-GO，0.545 GiB 体积地板确证（步骤 043）
